# Device risk scoring and policy

## Implemented behavior

`DeviceRiskEngine` stores integrity signals, calculates a bounded 0–100 score over the configured rolling window, groups reasons, and records each calculation with a policy version. It updates the device's current score for the admin dashboard. Expired signals no longer affect the score. Configurable thresholds and per-signal points label scores low, medium, or high; audited dashboard settings update those operational values. Registration records missing, failed, or verified attestation signals. The request middleware records replay, invalid signature/session, expired timestamp, unauthorized device, block-rule, and release-verification events when a registered device is known. A signed `/integrity/report` endpoint accepts only the native root, emulator, debugger, debug-build, instrumentation, runtime-hook, VPN, and basic network transport indicator names. Android reports VPN/Wi-Fi/cellular/Ethernet from active network capabilities; these are best-effort client signals. These remain client-modifiable review signals and cannot trigger automatic blocking.

Critical signature/release failures still deny the triggering request in middleware; they do not depend on the numerical score. Risk values never automatically block or revoke a device. The dashboard shows the high-risk device count, and the admin device detail API returns risk history and explanations. A transition into the high-risk level creates one deduplicated `app_security_alerts` record per device, policy version and date; crossing repeatedly while already high does not spam the alert list. Authorized administrators can acknowledge an alert with a required note, which creates an audit event. Optional email delivery uses a queued job on the `security` queue and requires explicit recipient and mail/queue configuration. Existing approve/reject/block/revoke actions remain explicit, reasoned admin transitions.

Configuration includes `KY_SECURITY_RISK_ENABLED`, `KY_SECURITY_RISK_WINDOW_HOURS`, `KY_SECURITY_RISK_POLICY_VERSION`, the existing review/high thresholds, and per-signal point settings such as `KY_RISK_REPLAY`, `KY_RISK_MISSING_ATTESTATION`, `KY_RISK_FAILED_ATTESTATION`, and `KY_RISK_REGISTRATION_VELOCITY`. Registration velocity uses `KY_SECURITY_REGISTRATION_VELOCITY_WINDOW` (default 900 seconds) and `KY_SECURITY_REGISTRATION_VELOCITY_THRESHOLD` (default 5 new registrations) and the admin can tune its risk points. Cross-account public-key reuse is also a configurable high-severity review signal (`KY_RISK_CROSS_ACCOUNT_KEY_REUSE`, default 35); registration uses a shared-cache lock keyed by an HMAC of the fingerprint so concurrent requests on multiple app nodes cannot both silently pass the initial check. Lock acquisition fails closed with a retryable 503 if contended. Use shared Redis cache in a multi-node deployment and configure trusted proxies so the IP comes from the actual connection rather than an untrusted forwarded header.

## Limits and next signals

Root, emulator, and instrumentation reports are client heuristics, not proof that the device is compromised. A modified client can omit or fabricate them; they add review context only. Daily device intelligence counts authorized requests and changes in server-observed public IP using an HMAC hash; it does not retain raw IP history. VPN and basic transport reports are implemented as low-confidence review signals. Registration velocity is implemented as a server-observed, short-lived cache counter keyed by an HMAC of the source IP. At the configured threshold it adds a configurable review signal and alert and withholds customer auto-approval; it never blocks automatically. Configure trusted proxies carefully and treat shared NAT networks as a possible false-positive source. Cross-account public-key reuse analysis checks whether the exact public-key fingerprint is already bound to another account. It flags the new registration, withholds customer auto-approval, adds configurable risk points and raises a review alert without blocking; a shared installation UUID with separate account-bound keys is not treated as abuse. Targeted user inbox notifications are implemented for registration and device-state changes; FCM push delivery is optional and remains disabled until configured. Asynchronous risk recalculation, automated false-positive classification, and policy experiments are not implemented. General Manager and IT Admin can manually mark non-critical signals confirmed or false positive with a reason; false-positive dispositions are excluded from later rolling scores and audited, while critical cryptographic failures remain counted and cannot be dismissed. Admin event alerts and queued email delivery are available when configured. No location data is collected.

Root/emulator/VPN indicators must remain review inputs, not proof of compromise, and must not independently trigger blocking. Keep manual state transitions audited until those signals have been tested against supported devices and false-positive behavior is understood.
