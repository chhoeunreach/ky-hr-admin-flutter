# Security administration

## Current surface

The Laravel browser UI is `/admin/app-security`, protected by the existing admin guard and permission middleware. The dashboard provides device counts (including high-risk), current release, recent devices, latest risk explanations, release records, and a validated policy form. JSON read endpoints are under `/api/admin/app-security`. Device rows display the latest attestation result and its reason. Dashboard data contains total/pending/approved/blocked/revoked/high-risk counts, active session count, current release and ten recent security events. The page includes a 14-day installation trend, current low/medium/high risk distribution, review-threshold registration count, and categorized signature, replay, attestation, release, and session anomaly events. Analytics are visible only to device managers and audit viewers; customer-support and staff-approval-only accounts do not receive the broader dataset.

Device list supports status/search and pagination; JSON list also accepts user type and per-page filters. Device detail hides the public key and returns recent sessions, risk-score rows and audit history. The browser UI links to a paginated session list for each manageable device; an administrator can revoke one live session with a reason and password step-up, invalidating its token hashes and recording an audit entry. Staff-approval-only administrators are restricted to staff sessions. Device actions are approve, reject, block, unblock, revoke and require re-registration, each requiring a reason. Re-registration retires the current key fingerprint, revokes sessions, and lets the client create a new attested key; the old key is denied at registration and on protected API requests. For a controlled key rotation while the old key is usable, verify ownership and use **Require re-registration**. If the key is unavailable or the app was reinstalled, the client creates a new per-install identity; verify ownership and revoke the stale device record before the new registration proceeds. Reject is limited to pending devices; blocked devices preserve their prior status for unblock; revoke is terminal. Reject/block/revoke invalidate sessions. Release UI supports upload, activate and revoke with audit reasons for activation/revoke.

## Permission assignment

The existing permission system now has distinct keys: `app_security_view`, `app_security_device_approval`, `app_security_devices`, `app_security_releases`, `app_security_settings`, `app_security_audit`, `app_security_alert_ack`, and `app_security_customer_support`. The legacy `app_security_manage` grants all App Security operations. The dashboard lists deduplicated high-risk alerts for authorized audit viewers. Administrators with the alert-acknowledgement permission can acknowledge an alert with a required reason; acknowledgement is audited. Optional email alerts are queued only when configured. The Super Admin dashboard panel assigns explicit App Security tiers to browser administrators and requires a reason for each audited change. Existing admins are seeded as Super Admin to preserve their current access; newly added administrators require an explicit assignment.

The dashboard includes a date-filtered CSV export of the administrator audit trail at `GET /admin/app-security/logs/export`. Exports default to the previous 90 days, are capped at 100,000 rows, stream in bounded batches, mark spreadsheet formula cells safe, and create an audit record containing the export filters. The `app_security_audit_export` permission is granted to IT Admin and Auditor; Super Admin and the legacy full-access permission also qualify. Runtime device security events remain available through the existing JSON logs endpoint.

Role tiers: Super Admin has full access; General Manager gets view, device control, audit; IT Admin gets view, device control, releases, settings, audit and export; HR Admin gets view and staff device approval; Auditor gets view, audit and export; Customer Support gets only customer device status. Staff-approval-only users cannot change customer devices or block/revoke installations. Customer-support-only responses omit keys, sessions, installation identity and risk data. Registration-velocity and attested OS/patch-policy failure risk points are configurable in Security Settings. Minimum OS/patch values are deployment environment settings; approval is rejected while the configured attestation floors are unmet. Cross-account public-key reuse raises a review alert and prevents customer auto-approval without automatic blocking; sharing an installation UUID with separate account-bound keys is allowed. The dashboard exposes attestation verification status and reason but not raw certificate-chain evidence; automated false-positive classification is not implemented. General Manager and IT Admin can manually review risk signals from device details; each disposition requires a reason, is audited, and a false-positive decision recalculates the rolling score. Critical signals cannot be dismissed; auditors retain read-only visibility. Device actions, release activation/revocation, administrator role changes, policy changes, and risk reviews require the current administrator password through implemented, per-account/IP-rate-limited step-up reauthentication. Queued administrator email alerts and browser alert acknowledgement are implemented. Pending registration and device approval, rejection, block, unblock, and revocation create a targeted mobile inbox entry and optionally send FCM through the existing sender; FCM is implemented but deployment-disabled by default.

## Device count policy

Security Settings provides independent maximum registered-device counts for staff, customers and administrators. A value of `0` means unlimited for backwards compatibility until a cap is selected. A new registration over the cap is rejected with HTTP 429, retains the existing device records, and creates a medium-severity security event/alert. Re-registration of an existing installation does not consume another device slot. User-row locking serializes registrations for the same account.

## Operator action notes

- Approval does not grant business permissions; existing user role and mobile permissions continue to govern API functions.
- Blocking and revocation take effect on the next server request; disconnected devices cannot receive immediate status.
- Every device action stores actor, reason, previous/new state, IP, user agent and timestamp.
- Release upload is immutable by package/version code; upload a new version for corrections.
