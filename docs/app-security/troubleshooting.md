# Troubleshooting

| Symptom | Likely cause | Checks and recovery |
| --- | --- | --- |
| `/app` says no release is available | No active release exists or package config differs | Check App Security releases and `KY_SECURITY_PACKAGE`; upload/verify/activate the signed APK. |
| APK upload reports publication is not configured | Missing/invalid `aapt`, `apksigner`, or trusted signer list | Check absolute executable paths and fingerprint formatting as the Laravel service user; do not put keystore secrets on the web server. |
| APK rejected as unknown signer/package | Uploaded APK does not match configured package or trusted certificate registry | Compare `aapt`/`apksigner` output to production build facts. Do not add a fingerprint until ownership is independently confirmed. |
| Client reports `releaseVerificationFailed` | Release check returns non-200 or server has no active release | Inspect response status and Laravel release registry; check active status, version code and signer. |
| Client reports `pendingApproval` | Device registration is accepted but policy requires admin review | Find installation UUID/device UUID in the admin list; approve/reject with reason. |
| Client reports `blocked` or `revoked` | Device state or block rule denies access | Review device detail and audit history. Unblock only a non-revoked device; revoked devices are terminal. |
| API returns `401 app_security` | Missing/expired session, timestamp, signature, bearer token or request mismatch | Confirm the request uses the signed wrapper and exact raw URI/body. The client clears session state and rechecks on the next call; the failed mutation is not retried. |
| API returns `409` replay or a registration-required screen persists | A nonce was reused, or this account's installation UUID is bound to a different key | First distinguish a request replay from key recovery. When the old key is available and an administrator requested a controlled key rotation, use **Require re-registration** with a reason and password step-up; the server retires the old key and revokes sessions. If the key is unavailable or the app was reinstalled, the client creates a new per-install identity; a device manager verifies ownership and revokes the stale record before the new installation registers under the normal approval policy. The user then taps **Check again**. Never bypass this flow by editing the database, reusing an old key, or repeatedly clearing app data. |
| API returns `423` | Device not approved, blocked/revoked or no longer authorized | Check device status, release/block rules and user binding. The server remains authoritative. |
| API returns `426` | Mandatory release update policy | Verify latest active release/minimum version and download endpoint. Older archived releases remain optional unless the active release or minimum-version floor requires an update. |
| Client reports unsupported Android / API returns `428` | Device SDK is below the installed APK minimum or cannot run a mandatory release | Check the device Android SDK and the release metadata `minimum_android_sdk`. Install on a supported Android device; a too-new optional release is not prompted. |
| Key creation fails | Android Keystore unavailable, OS/device policy, or StrongBox/TEE failure; an existing key may also have been invalidated | Check Android device logs and supported API. If the key was lost or invalidated, use the administrator-managed recovery above before retrying. The client creates a new installation identity and does not silently replace a server-registered key. |
| Attestation appears pending indefinitely or unverified | The Laravel verifier is implemented, but verification stays fail-closed without the current trust-root bundle and a fresh Google attestation status snapshot | Provision and validate the complete Android attestation root bundle at `KY_SECURITY_ATTESTATION_ROOTS_PATH`, run the scheduled `app-security:refresh-attestation-status` command, and verify its freshness before enabling required attestation. Do not manually mark the evidence trusted. |
| Protected screens show generic API errors after admin revoke | API call received a server denial but a screen has no security-gate presentation | The request is blocked; sign out/reopen to run the full startup gate, or add a common app-level authorization-state listener. |

Do not log access/refresh tokens, private key material, full attestation evidence or user-sensitive request bodies when diagnosing failures.


| Release startup says API host is unpinned or pinning is not configured | Release Dart defines omitted the approved host or SPKI key set | Build with `KY_SECURITY_PINNING_ENABLED=true`, the official host, and verified primary plus backup SPKI pins. Confirm key rotation against staging; do not disable TLS or use HTTP as a workaround. |

| Client stays restricted while offline | No unexpired signed lease is cached, offline grace is zero, the signing-key ID is missing from the APK, the install/account/release does not match, or the device rebooted | Reconnect, verify the lease key ID and signing configuration, and check the authorized heartbeat; offline leases are default-off and device-bound. Do not increase grace as a workaround for key/signature failures. |
