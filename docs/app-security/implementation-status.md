## Implemented in this change

- Added the App Security relational schema, security settings, models, signature/release/device/session services, API endpoints, security middleware, and `app_security_manage` permission migration.
- Added security middleware to the authenticated existing API groups. Enforcement is feature-flagged off by default until the mobile client rollout is complete.
- Added admin device listing, filtering, approval/rejection, reversible block/unblock, revoke, dashboard JSON, and audit events.
- Added an audited, password-step-up-protected “require re-registration” action. It retires the old key fingerprint, revokes sessions, and requires the app to create and attest a different key before the device can register again.
- Added separately configurable staff, customer and administrator registered-device caps. Zero means unlimited until configured; registration enforces a selected cap under account-level row locking and alerts on rejected excess registration.
- Added a release workflow: APK validation through configured Android SDK `aapt` and `apksigner`; package and trusted signer validation; APK SHA-256; immutable versioned private storage; draft/activate/revoke; release audit records; public `/app` page; controlled latest and versioned APK downloads; version metadata and checksum endpoints.
- Added Android Keystore P-256 key generation, best-effort StrongBox with TEE fallback, public key export, signing, app identity and signing certificate reporting. Release integrity accepts a validated comma-separated signer allowlist for planned certificate overlap; Laravel still verifies the exact signer registered for each APK release. Existing app integrity channel and NFC/device clock code are retained.
- Android device keys now use separate account aliases, so a second staff/customer account gets a fresh challenge-bound key while existing server-registered installations can select their already-bound legacy key by its server-provided public-key fingerprint.
- Installation identity is held in a dedicated Android preferences file excluded from cloud backup/device transfer, while normal app backups remain enabled. Upgrade migration preserves the prior ID only when the existing Android Keystore key confirms install continuity; unavailable server-bound keys rotate to a new install ID and require administrator review of the stale registration.
- Added server-side Android Key Attestation path, challenge, key, package/signer, hardware key-parameter, locked-device and Verified Boot checks. The verification stays fail-closed unless external trust roots and fresh Google status data are configured; a scheduled command refreshes the private revocation snapshot.
- The admin device list shows the latest attestation status and its review reason.
- Added `DeviceRiskEngine` for configurable server-observed signal scoring, rolling-window expiry, explained/policy-versioned risk history, and admin high-risk counts/reasons. Replay and invalid-signature events update scores; security middleware still denies the triggering request independently, and scores never auto-block users.
- Added a signed heartbeat endpoint and Flutter heartbeat client. The client follows the configured interval, renews a nearly expired session through existing rotation, and reports authorization loss/update-required/offline states without retrying the protected business request.
- Added daily privacy-minimized `app_device_intelligence` summaries for already-authorized signed requests: request counts, version facts, and counts of HMAC-hashed server-observed public-IP changes. Added scheduled cleanup for expired nonce/challenge rows, aged signals/risk snapshots/logs/intelligence summaries, and encrypted attestation evidence after its configurable retention period (90-day default); evidence summaries remain for review.
- Added deduplicated alerts for high-risk transitions, high/critical server-observed signals (including invalid signatures, replay, attestation failures, registration velocity and cross-account key reuse), new installations, device state changes, and release publication/revocation; added an audited acknowledgement workflow, admin UI/JSON feeds, and optional queued email notification on the `security` queue; mail notification stays off until recipients and queue/email configuration are supplied. Lower-severity signals remain in risk history without individual alerts to limit noise. Added admin JSON feeds for releases, logs, risk reports, and intelligence; the existing browser dashboard now supports audited runtime policy settings for approval, attestation, TTLs, risk thresholds and signal points. `KY_SECURITY_ENABLED` remains controlled by deployment environment.
- Added granular admin permissions for viewing, staff device approval, full device control, release management, policy settings, audit logs and customer-support status. Customer-support responses are restricted to customer status, and staff-approval permission cannot block/revoke devices or alter customer devices. Legacy `app_security_manage` retains full access.
- Existing mobile role permissions remain authoritative. A unique legacy action permission continues to imply its menu when no explicit menu grant exists, while shared action permissions never infer one of their sibling menus; global feature switches still hard-deny access. Employee chat uses its established `view_employee_chat` / `send_employee_chat` abilities. Before production rollout, review each `mobile_permissions.functions` entry against real role grants and explicitly assign newly introduced function abilities; unmapped access must remain denied.
- Added a Flutter security client for release verification, challenge/response registration, session open/refresh, and a reusable canonical signed-header builder backed by the Android Keystore key. Fresh login and saved-session startup check server policy and route enforced-but-unauthorized installs to a retry/update status screen.
- Android key selection now confirms that the private Keystore key remains usable as well as matching its server-registered public fingerprint. A missing or permanently invalidated key routes to administrator-managed recovery; the app does not silently bind a replacement key. Manager and security-gate regression tests cover the recovery state.
- Added a shared HTTP wrapper for buffered API calls, injected HTTP clients and multipart requests; migrated the app's direct authenticated API calls. Multipart data is spooled to a private temporary directory so exact request bytes can be hashed before upload. Added a Dio interceptor for the protected POS reporting client, including disk-spooled FormData uploads.
- The public server-version, server-selection, and device-clock probes now route through `KyCertificatePinning.clientFor`; release requests to configured official API hosts use SPKI verification, while injected clients and non-official hosts retain their existing behavior.
- The monthly attendance-summary dashboard refresh also uses the shared signing/pinning transport while preserving its injected HTTP client; the focused Flutter regression suite passes all 28 tests.
- Laravel attestation parsing now requires one fully consumed BER value, validates KeyDescription, RootOfTrust, and Application ID field types, and rejects trailing values and extra fields; signed synthetic-chain tests cover malformed inputs.
- The verifier implements Android's documented expired factory certificate exception only for chains anchored to subject serial `f92009e853b6b045`; CRL revocation remains mandatory and RKP validity checks remain strict.
- Protected API `401`, `423`, and `426` responses now invalidate cached client authorization; `401` also clears the in-memory device session so a later call rechecks policy and can recover only if Laravel still authorizes the installation. The failed business request is never replayed automatically.
- The existing account logout endpoint is Passport-authenticated, rate-limited and exempted from device/business authorization middleware so blocked users can sign out; the security gate exposes that path. The endpoint still revokes the caller's App Security session when a session UUID is supplied.
- Security middleware now records selected authentication/signature/replay failures in `app_security_logs`, without logging request bodies or tokens; nonce uniqueness conflicts return 409, while other database failures return 503.
- Device installation UUID and public-key fingerprint are now account-scoped for uniqueness, allowing staff and customer accounts to register separately on the same app installation while keeping approval, risk and session records user-bound. A guarded rollback refuses to restore the old global UUID constraint if accounts share an installation.
