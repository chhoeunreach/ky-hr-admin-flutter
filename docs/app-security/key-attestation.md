# Android Key Attestation

## Implemented verifier behavior

Laravel validates the submitted certificate path against PEM trust anchors supplied outside the repository, checks certificate signatures and validity, checks each non-root certificate against a fresh Google status-list snapshot, and parses the Android Key Attestation extension. It selects the first extension encountered from the root toward the leaf, as Android requires, and ignores later copies. If an RKP provisioning-information extension is present, the selected key-attestation extension must be on the immediately subsequent certificate. The embedded challenge is bound to the decoded single-use registration challenge, and the selected attestation certificate's public key is compared with the registered P-256 key. The verifier also checks the Android application ID package and signing-certificate digest, and requires a hardware-enforced P-256 EC key with SHA-256 and sign/verify purposes. It requires a locked device and Verified Boot state. A valid result records only a minimal summary and sets the device attestation level to TEE or StrongBox. Submitted certificate chains are encrypted as evidence with an expiry from `KY_SECURITY_ATTESTATION_EVIDENCE_RETENTION_DAYS` (default 90 days). The scheduled cleanup clears expired ciphertext but retains the verification status and summary for audit.

`app-security:refresh-attestation-status` fetches Google's status JSON, validates its shape, honors the response cache TTL, and atomically updates a private snapshot. The scheduler runs it every six hours. Failed requests or malformed responses leave the last good snapshot untouched. The verifier fails closed to pending/unverified if trust roots are missing or the status snapshot is absent/stale. Invalid evidence receives elevated review risk. `KY_SECURITY_HARDWARE_ATTESTATION=required` rejects registration unless verification succeeds.

The admin device list shows verification state and the verifier's reason for a pending result. ASN.1 parsing requires a single fully consumed value and validates the expected KeyDescription, RootOfTrust, and Application ID field types. Automated tests cover a synthetic trusted certificate chain, a non-leaf attestation extension with a later duplicate, challenge and package mismatch, trailing ASN.1 data, extra KeyDescription fields, missing trust roots, malformed chains, CRL freshness and safe snapshot refresh.

## Deployment prerequisites and limits

- Provide Google’s official root bundle at `KY_SECURITY_ATTESTATION_ROOTS_PATH` (or default the path in deployment configuration) before enabling required attestation. Google publishes the PEM roots as a JSON array at `https://android.googleapis.com/attestation/root`; retrieve it over validated HTTPS, verify each certificate is an active CA trust anchor, preserve the last-known-good bundle, and install the complete current set with restrictive permissions. Google’s current guidance lists a new root that began signing chains on 2026-02-01, so do not provision only the older root. Root rotation and manufacturer trust decisions remain operator-controlled; this repository intentionally ships no trust anchors.
- Configure `KY_SECURITY_ATTESTATION_CRL_PATH` only if the default private Laravel storage path is unsuitable. Keep the file outside the web root and ensure the Laravel scheduler runs. The first successful scheduled refresh is required before any attestation can be marked verified.
- Expired factory attestation certificates are accepted only when the validated chain anchors to the factory root whose subject serial number is `f92009e853b6b045`, matching [Android's documented exception](https://developer.android.com/privacy-and-security/security-key-attestation#expired-factory-keys-still-trustworthy). Revocation checks still apply to every non-root certificate. RKP and other chains continue to require current certificate validity.
- OS version and OS patch claims are included in the minimal verification summary. Optional minimum floors are enforced at registration, admin approval, session issue/refresh, and protected requests; missing/unverified claims fail closed when a floor is enabled. Evidence expiry is automated; retention duration and the requirement to preserve verification summaries should be reviewed against applicable legal and business policy. The claim formats follow the Android AOSP attestation schema: `MMmmss` for OS version and `YYYYMM` for OS patch level.
- The parser is a custom PHP implementation tested with synthetic DER certificates. Android recommends its maintained Kotlin attestation-verification library; further review/fuzzing and tests with current RKP and OEM chains are still required before production enforcement.
- Manufacturer-specific trust roots beyond the configured roots, certificate transparency, and end-to-end hardware/device tests have not been completed.

Android's current guidance requires trust-chain and revocation checks and documents the extension schema at [AOSP Key and ID attestation](https://source.android.com/docs/security/features/keystore/attestation). Google publishes the [attestation root bundle](https://android.googleapis.com/attestation/root) and revocation status list from its [Android Key Attestation verification guidance](https://developer.android.com/privacy-and-security/security-key-attestation). Download the root bundle for controlled manual provisioning; do not replace trust anchors solely from an unreviewed scheduled response.
